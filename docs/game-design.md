1. ゲーム概要

ターン制RPG × プログラミングによる戦闘自動化。プレイヤーは弱い勇者に手動コマンドを与え、後に日本語風コードを組み立てて戦闘を自動化する。敵はランダムに行動せず、最初から公開された規則に沿って行動する。プレイヤーは規則を読み、対応するアルゴリズムを設計して攻略する。

• 勇者の攻撃は常に 1ダメージ。
• 勇者は 一度被弾すると即死（HP管理なし）。
• 敵の行動は 決定的・反復可能・原則すべて公開。
• 手動での攻略は可能だが、後半ほどコード化が有利。
• 死亡しても書いたコードは残り、RETRY＝デバッグとなる。
• ゲーム内では操作やコードを「神託」と位置づけるが、UIでは通常の「攻撃」「防御」「CODE」「RUN」などの表現を使う。

2. 対象環境・技術方針

• ブラウザでプレイ。スマートフォン操作を前提にし、PCでも使えるレスポンシブUI。
• MVPは HTML / CSS / JavaScript の単一HTMLファイルで構築し、動作確認後にモジュール分割。
• コード実行には eval を使用せず、独自の構文解析器と戦闘インタプリタを設計する。
• 将来、セーブデータは localStorage などへ保存。コードのテキスト書き出し／取り込みも予定。
• まずは戦闘ループの完成を優先し、物語・演出は後回し。

3. 戦闘の確定仕様

3.1 ターン進行

1. プレイヤーが 1行動を実行（手動ボタン／RUN中の命令）。
2. プレイヤーの攻撃で敵HPが0になった場合、その場で勝利。敵は行動しない。
3. 敵が、公開済みの行動規則に従って 1行動を実行。
4. 生存していれば次ターンへ進む。

表示中のTURN番号は現在のターン。通常敵は同じ行動パターンを末尾まで実行すると先頭へ戻る。行動位置は自動ハイライトしない（必要なら後で表示補助を検討）。

3.2 勇者コマンド

|コマンド  |効果                                            |
|------|----------------------------------------------|
|攻撃    |敵に1ダメージ                                       |
|防御    |敵の「攻撃」「特技」に対応                                 |
|回避    |敵の「魔法」に対応。通常の攻撃への対応は仕様上の整理が必要（現プロトタイプでは攻撃にも有効）|
|覚える／記憶|そのターンの敵行動を観察し、終了時に変数 `記憶` に保存する。1ターン消費        |

設計上の基準：「攻撃／特技には防御、魔法には回避」が基本解。現行の仮実装では回避が攻撃にも有効になっているため、正式な対応表への修正が必要。

3.3 敵の行動

|行動|概要                |
|--|------------------|
|攻撃|防御で対処する基本攻撃       |
|タメ|次に特技を行う準備。攻撃機会    |
|特技|敵固有の決定的な技。基本は防御で対処|
|詠唱|次に魔法を使う準備。攻撃機会    |
|魔法|回避で対処             |
|待機|攻撃機会              |

• タメ → 特技、詠唱 → 魔法 は固定。
• 特技は連続行動・繰り返し・ターンの偶奇による分岐なども可能。
• 次の行動だけは表示せず、行動パターン全体を番号付きリストで提示。
• 敵の行動に乱数・隠しパターンを使わない。

3.4 死亡・勝利・RETRY

• 被弾すると即死亡、コード実行中なら即停止。
• RETRYでは敵HP・ターン番号・敵行動位置・記憶・ループ等の戦闘状態を初期化。
• 現在のエディタ内容・保存済みコードは保持。
• RETRYしても自動でRUNしない。
• 死亡画面からコードを修正可能。LOGで直近の失敗を確認可能。
• 戦闘終了後は勝利／死亡ログを見られる。
• RETRYはゲーム全体で累積カウントし、結末に反映。失敗によるその他のペナルティなし。

4. 記憶システム

覚える をプレイヤーが選ぶと、そのターンの敵行動が終わった後に記憶内容が更新される。

例：

TURN 5: 勇者「覚える」 → 敵「詠唱」 → 記憶 = 「詠唱」
TURN 6: 記憶が「詠唱」なら、勇者「回避」 → 敵「魔法」

• 戦闘開始時の記憶：なし。
• 新しい 覚える を行うまで記憶は維持。
• プレイヤーコードは敵の現在行動を直接参照できない。参照は記憶や公開されているターン等を介して行う。
• 最終戦の形態変化では記憶を引き継ぐ。

5. CODE / RUN（将来実装）

5.1 基本動作

• 第1章は手動のみ。第1章クリア後にコンソール解放。
• エディタは戦闘画面内に常時表示（解放後）。編集自体はターンを消費しない。
• 手動とRUNを混在可能。
• RUNはプログラムを実行し、完了・勝利・死亡まで操作を返さない。中断・編集・手動介入不可。
• 正常終了して敵が生存している場合、現在の戦闘状態のまま操作を返す。
• 低速・高速の実行方式を設ける（速度指定の構文は未決定）。
• 1000行まで。複数のプログラムを保存・読み込み・複製・テキスト入出力可能。別プログラムの呼び出し機能は設けない。
• テキスト入力と、構文が正しく組み上がるコマンド式入力補助を切り替えられるようにする。

5.2 日本語風構文

完全な「なでしこ」互換ではなく、ゲーム専用の日本語風言語。

攻撃する
防御する
回避する
覚える

5回繰り返す
    攻撃する
ここまで

もし、記憶 = 「詠唱」ならば
    回避する
違えば
    防御する
ここまで

• 逐次処理、回数繰り返し、もし／違えば／違えばもし。
• 論理演算 AND / OR / NOT。
• カウンタ付き for、四則演算・剰余 + - * / %、比較。
• 使用可能な値：記憶、現在の ターン、敵 HP、ループカウンタ、数値・文字列。
• 自由なユーザー定義変数は当面なし。
• 未解放構文は「まだ覚えていない」として実行不可。
• 構文エラーがある場合RUN不可。構文エラーだけでは死亡しない。
• 構文上正しくても作戦が間違っていれば、そのまま実行して死亡しうる。論理的な危険を先回りして警告しない。

5.3 戦闘後ログとデバッグ

• 詳細ログ・リプレイは戦闘終了後に開ける。保存は直近1戦のみ。
• 記録：TURN、手動／RUN、勇者行動、敵行動、記憶、成功／被弾、RUNでの実行行。
• 死亡時は死亡ターン付近、勝利時は最終ターン付近から閲覧。
• RUN中の死亡行を選ぶとエディタの該当行へ移動・強調。ただし正誤は自動判定しない。
• 勝利後もコードを編集・保存して改善できる。

│ │ 最新ログ1行  │ │ TURN 3 │    │

8. 章構成（全15章）

各学習章は基本3戦構成：①構文の基本 ②数値等を変えた類題 ③応用。第1章は手動戦闘3戦。四天王は各1戦。

|章 |内容               |章クリア後の解放      |
|--|-----------------|--------------|
|1 |手動戦闘：防御、回避、複合    |コンソール・逐次処理    |
|2 |逐次処理             |回数指定の繰り返し     |
|3 |単純な繰り返し          |`もし`          |
|4 |単純条件分岐           |`違えば`         |
|5 |if / else        |`違えばもし`       |
|6 |多分岐              |`覚える`・`記憶`    |
|7 |覚える・記憶           |AND / OR / NOT|
|8 |論理演算             |カウンタ付きfor     |
|9 |カウンタ付きfor        |算術演算          |
|10|算術演算・剰余          |新規構文の学習完了     |
|11|四天王①：繰り返し×条件分岐   |—             |
|12|四天王②：入れ子の繰り返し    |—             |
|13|四天王③：入れ子の条件分岐    |—             |

• 課題構文を強制使用させない。手動や別アルゴリズムで突破してよい。

• 例をクリップボードにコピー可能、エディタへ自動挿入はしない。
• 四天王は手動では非常に長いが、正しい高速RUNなら概ね30秒〜1分の想定。
• 第14章は3の倍数／5の倍数／両方／その他など、評価順序も考える問題。解法は複数許容。

9. 最終戦の特別ルール

• 邪神自身は戦闘に出ず、邪神がコードで制御する最強モンスターと戦う。
• 3形態：①攻撃重視・低耐久 ②低攻撃・高耐久 ③攻守均衡。形態ごとに外見・敵コード・HPが変わる。
• 将来の形態のHP・コードは到達するまで非公開。
• 形態を倒してもRUNは止まらない。勇者のコードの実行位置・ループ状態・記憶を引き継ぐ。
• 形態移行時はTURNが1に戻り、敵HP・敵コードが更新される。
• 死亡時はPhase 1からやり直し。エディタ内のコードは保持。
• 実行を形態境界で止めたい場合は、プレイヤー自身がその位置で終わるコードを書く必要がある。

10. 物語・設定（概要のみ、制作優先度は低）

• 当初は「神に選ばれた寡黙な勇者が魔物を倒す」という普通のRPGに見せる。
• 勇者は開始から最後まで一言も喋らない。妖精は開始時から同行する、よく喋る非戦闘キャラ。
• 手動コマンドはその都度、RUNではコードの全体が一気に神の声（神託）として勇者に届く。
• 勇者は命令の意味・ルールを理解して実行できるが、そのプログラムで勝てるかは判断できない。
• 序盤の人々の噂や「昔、神の言葉に従って世界を救った勇者がいた」という伝承で、神の存在を少しずつ示す。
• プレイヤー＝神であることは序盤では明かさない。
• 第7章で妖精が勇者の記憶に触れ、神託を理解し、以後神の声を聞けるようになる。
• 神＝プレイヤーと邪神はゲーム世界の外側にいる、対称的な命令者。終盤でモンスターもコードで動いていたと分かる。
• 最後は邪神が三度のコードの試みを諦め、魔物は停止・消滅。勇者と妖精は神と別れ、勇者は無言で画面のこちら側に頷く。
• 細かな台詞、伝承・過去の勇者の扱い、シナリオの具体的展開は未決定。

11. エンディングと周回

累計RETRY数により、邪神の最終台詞と記念碑の碑文・エンドカードを変える。別れのシーンは共通。

|ENDING|RETRY数|記念碑の方向性              |
|------|-----:|---------------------|
|無謬の神  |0     |一度も敗れることなく、世界を救った神   |
|導きの神  |1〜3   |幾度か道を改め、正しき導きで世界を救った神|
|不屈の神  |4以上   |幾度倒れようとも諦めず、世界を救った神  |

• エンドカードに実際の RETRY: n を表示する。
• タイトル画面に3枠のENDING COLLECTION。未取得の条件は伏せる。
• NEW GAME：物語・習得構文・RETRY数リセット。保存コードは残す。
• 強くてNEW GAME：物語・RETRY数リセット。習得構文と保存コードは残す。
• 敵HP・敵行動は周回でも変えない。
• クリア済み章はSTORY／BATTLEで再訪可能。再戦で使ったRETRYも累計に含める。

12. 推奨実装順

1. 現在の戦闘UIを安定化：表示・最新ログ・TURN・モバイル画面を確認。
2. 戦闘エンジンの一本化：手動とRUNが同じ performTurn(action) を利用。
3. 敵行動テーブル：固定「攻撃」から複数行動の循環へ拡張。
4. コマンド完全実装：攻撃／防御／回避／覚える、被弾とRETRY。
5. 逐次プログラムの実行：行ごと解析→一行動ずつ→RUN終了／死亡／勝利。
6. 繰り返し、分岐、記憶、演算を段階追加。
7. 戦闘後LOG、保存、REFERENCE、章解放を追加。
8. 敵・四天王・最終3形態を実装し、調整。
9. 最後にシナリオ、演出、エンディングを統合。

次の実装目標（推奨）

攻撃・防御・回避の既存ボタンは維持したまま、「敵の行動パターンを配列で管理する」こと。 その次に「覚える」ボタンを有効化し、すべてのコマンドを一つのターン処理へ統合する。RUNを後付けしても同じロジックが再利用できる構造を目指す。
